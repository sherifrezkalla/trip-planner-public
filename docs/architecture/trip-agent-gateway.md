# Trip-agent gateway and authority foundation

Status: shipped and production-verified on 2026-09-22 through PR #87 (private development record); see [release evidence](trip-agent-gateway-release.md). This is Plan 1 of [WhatsApp-first V2](../superpowers/plans/2026-08-29-whatsapp-first-v2-plan-index.md). Plan 2 supplies connector onboarding and the live OpenClaw/Hermes/WhatsApp connection. The foundation has no end-user setup UI, proactive engine, or replacement traveler interface.

## Boundary and alternatives

One organizer-owned OpenClaw or Hermes connector owns the WhatsApp session and presents structured commands to Trip Planner. The planner owns canonical state, permissions, proposal settlement, reservation locks, and audit. The connector is neither a traveler nor the trip owner. Its bearer resolves one connection and one trip; it cannot supply a different trip or establish organizer authority through a display name.

MCP provides typed, inspectable tools around the existing domain services. Driving the board UI was rejected because conversational actions need stable authority, replay, and failure semantics that clicks cannot guarantee. Giving the connector database credentials was rejected because it would bypass those rules and expose unrelated trips and private fields. The gateway reuses `createPlanProposal`, `createSuggestionProposal`, `settleProposal`, protected SQL operations, itinerary lookup, and the existing reservation-assistance workflow.

HTTPS bearer authentication is the selected foundation transport because the supported generic MCP clients lack a portable dynamic body-signing hook. A provider-specific request-signing scheme would break the shared connector boundary. Bearers are revocable, and action-layer identity binding plus durable idempotency provide mutation replay safety. OAuth or mTLS remain later transport hardening; they are not implemented here. A bearer holder must still satisfy group, scope, mapping, policy, and current-state checks.

## Protocol and wire behavior

This gateway implements only MCP 2026-07-28 Streamable HTTP: stateless and POST-only; legacy GET and DELETE receive 405. This is a revision-specific restriction, not a rule for every historical Streamable HTTP implementation. The official [2026-07-28 transport specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) and [release notes](https://blog.modelcontextprotocol.io/posts/2026-07-28/) describe the removal of the GET stream and protocol sessions. Connectors must initialize their modern client and make calls through POST; they must not depend on old GET/SSE/session behavior.

The repository lockfile resolves [`@modelcontextprotocol/server`](https://www.npmjs.com/package/%40modelcontextprotocol/server?activeTab=versions) and [`@modelcontextprotocol/client`](https://www.npmjs.com/package/%40modelcontextprotocol/client?activeTab=versions) to 2.0.0. The server is a runtime dependency; the client is development-only and exercises real `StreamableHTTPClientTransport` calls in tests. These are the official split packages described in the SDK's [split-package guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/get-started/packages.md).

`app/api/mcp/route.ts` validates the request hostname against `TRIP_AGENT_ALLOWED_HOSTS`, then checks that any supplied Origin has the same origin as the request URL, then authenticates the exact `Bearer` header before delegating the original request. Boundary failure is 403, invalid credentials are 401, a paused connection is 403, and database/authentication unavailability is 503. GET/DELETE also pass through this boundary; only valid authenticated requests reach the SDK's 405 response. Every MCP response, including delegated SDK responses and failures, has `Cache-Control: no-store`.

One module-level `createMcpHandler` routes requests with `legacy: "reject"` and `responseMode: "auto"`; its factory creates a fresh `McpServer` per protocol request. Authenticated trip context travels through the SDK's per-request `authInfo`, without copying the raw bearer into that context. No server session holds authority across requests.

Tools return `{ ok: true, data }` or `{ ok: false, error: { code, message, retryable, retryAfter? } }` in text and structured content. Every tool failure sets MCP `isError: true`. One closed catalog owns the public code, required generic message, and boolean retryability; caller, provider, database, and stored diagnostic text cannot enter messages. Unknown codes collapse to `database_unavailable`. Optional `retryAfter` is an integer from 1 to 86,400 seconds; malformed values are omitted. HTTP authentication and SDK input-schema validation retain their protocol-boundary responses.

Only `rate_limited`, `database_unavailable`, and `upstream_unavailable` are retryable by default. Policy, lifecycle, mapping, confirmation, reservation, expiry, conflict, and action-progress refusals are terminal. A context override can only disable retries. Persisted `failed`/`unknown` actions, uncertain vote/decision settlement, and caught failures after a possible action insertion or execution claim are terminal, including lost claim responses. A pre-action read outage can remain retryable; setup and announcement outages can remain retryable because their exact commands have transactional durable replay. The outer adapter catch is always terminal. This conservative boundary favors reconciliation over accidentally duplicating an uncertain write. It does not prevent an explicitly requested exact replay from recovering an already durable result.

Every validated result retains only its request/command UUID in application diagnostic metadata (`actionId` for commit); raw provider identities never enter metadata. An explicit research `status: "unavailable"` remains a successful description of missing information, never an empty-result claim or fabricated route.

## Storage and credential lifecycle

Migrations, in order: `supabase/migrations/20260829120000_trip_agent_gateway.sql` and `supabase/migrations/20260921120000_gateway_safe_traveler_removal.sql`, after the existing migrations.

| Table | Purpose and invariants |
|---|---|
| `trip_agent_connections` | One row per trip; provider is `openclaw` or `hermes`. A positive monotonic lifecycle generation separates replacement connector identities while preserving history. Stores lifecycle, scopes, two bounded policy booleans, optional agent phone/group label, credential and pairing digests, group/notice receipt digests, and timestamps. |
| `trip_agent_participant_mappings` | Lifecycle-scoped external participant digest, display hint, and suggested/confirmed/revoked traveler mapping. External identities and confirmed travelers are unique within `(connection_id, lifecycle_generation)`; composite constraints keep mapping and traveler in the same trip. |
| `trip_agent_actions` | Unique `(connection_id, lifecycle_generation, idempotency_key)`, actor digest, operation-specific normalized request, preview/fingerprint, authority, status/expiry, canonical references, bounded result/error, and announcement audit. Same-trip constraints protect connection, traveler, and proposal references. |
| `trip_agent_rate_windows` | Atomic fixed-minute counts keyed by connection, bucket, and window start; setup 30/minute, reads/research 120/minute, mutations/announcements 30/minute. Refusal returns `rate_limited` with retry-after before domain execution. |

All four tables have RLS enabled with no client-access policy. Public, anonymous, and authenticated roles have no direct table access; sensitive RPC execution is service-role-only. Trip-owned records cascade on trip deletion. Lookup indexes support credential/mapping resolution, confirmations, action history, and pending announcements. This is not a transcript store.

Pairing codes and bearer credentials are random 32-byte base64url secrets; only SHA-256 digests are stored. Inputs must be exactly 43 ASCII characters from `A–Z`, `a–z`, `0–9`, `_`, and `-`, without padding or whitespace. Bearer headers must be exactly `Bearer ` followed by one such credential. Case/spacing normalization and pairing-code trimming are forbidden; malformed values fail before digest/database lookup. Raw group, participant, and message identifiers are converted to connection-and-lifecycle-scoped HMAC-SHA-256 values using `TRIP_AGENT_IDENTITY_PEPPER`. Labels and display hints remain readable and are never evidence of identity. Keep that deployment secret stable across every instance; changing it invalidates existing identity comparisons and is not ordinary credential rotation.

The lifecycle is `pending → paired → active`, with `paused`, `revoked`, and `archived` controls:

1. Organizer POST issues a ten-minute single-use pairing code with only `connector.setup` scope. A pending code can be replaced. An existing paired/active/paused connection must first be revoked before replacement.
2. The public pairing POST accepts only the exact code and selected provider. It checks a 20-attempt/hour IP bucket first, then a separate 20-attempt/hour bucket derived only from the code's once-computed SHA-256 digest, then atomically consumes an unexpired, unused, provider-matched code. The digest bucket is domain-separated from IP and stored credential digests: one code shares its quota across IPs, while different codes still share the caller's IP quota. Either limit has the same 429 body and `Retry-After: 3600`; limiter outages fail closed. No plaintext code enters limiter or consume RPC arguments. Pairing returns the bearer once, connection/trip IDs, `status: "paired"`, and the canonical `/api/mcp` URL. It does not activate the connector.
3. The connector registers one group and suggested participant mappings. The organizer confirms mappings and explicitly configures operational scopes/policy. New or unknown participants stay unmatched.
4. Activation transactionally rechecks the paired connection, setup scope, bound group and metadata, valid saved policy, confirmed organizer mapping, privacy notice version `v1`, and the connector-supplied delivered receipt digest. Delivery remains a connector assertion; Trip Planner does not connect to the messaging provider to verify it.
5. Pause blocks subsequent authentication. Resume returns to active only if `activated_at` exists, otherwise paired. Revoke and archive clear credentials and pairing fields before returning, block later access, and cannot be resumed. A new POST may atomically start a fresh pending generation in the same per-trip row after either terminal state. That transaction increments the generation and clears all connector-owned metadata, group/notice binding, scopes, policy, and lifecycle timestamps. Earlier mappings and actions remain immutable audit history but cannot resolve, activate, confirm, announce, or consume current idempotency keys; the replacement must register and receive a newly confirmed human-organizer mapping.

Organizer PATCH rotation is the explicit API confirmation: a SQL transaction replaces the credential digest and writes its secret-free `trip_events` audit together. The new credential is returned once; the old one stops authenticating. Plan 2 must present a visible confirmation before invoking rotation. Other lifecycle writes use compare-and-set on `updated_at`, advancing it strictly beyond the observed version so concurrent or same-millisecond writes cannot revive or overwrite newer state. Last-seen telemetry is best effort and cannot decide authentication success.

The shared public-request limiter takes a transaction-scoped advisory lock derived from the bucket before count/insert; a transaction without that lock would oversubscribe simultaneous attempts. Unrelated buckets use independent locks. Expiry uses each bucket's own window so a one-minute lookup cannot erase an active one-hour pairing quota. A bounded global sweep removes abandoned rows after the maximum supported one-day window on subsequent traffic and skips locked rows. This retains cleanup without a global request lock; it is not a scheduled retention worker.

## Organizer API and onboarding boundary

Management uses header-only `x-trip-token` authentication, separate from the connector bearer, and requires an organizer who is not a bot. Connection GET returns `{ connection, mappings, recentActions }` with explicit redacted projections: only current-generation mapping management fields and at most 25 newest-first action summaries are included. POST accepts `{ provider }`; PATCH accepts `pause`, `resume`, `rotate`, `archive`, `update_policy`, or `update_metadata`; DELETE revokes. Participant PATCH accepts `confirm`, `remap`, or `revoke` for an existing current-generation same-trip mapping. Mapping changes and their audit event commit in one RPC with current-state guards. Pairing and both organizer route families set `Cache-Control: no-store` on successes and failures, including one-time pairing and rotation secrets.

The private action-confirmation endpoint accepts only `{ decision: "confirm" | "reject" }` and reads `x-trip-token` directly, with no query fallback. Only the current human organizer can use it, and responses are no-store allowlists. There is no connector tool for rotating credentials, changing permissions, retrieving documents, or supplying private organizer authentication.

Plan 2 must supply the curl-free organizer setup flow that presents these safe mapping/history summaries, provider configuration, and live end-to-end onboarding. The current REST endpoints alone are not a complete organizer experience.

## Tools and authority

The registered foundation tools are the three setup tools (`register_trip_group`, `get_trip_agent_readiness`, `activate_trip_agent`), three read tools (`get_trip_context`, `get_today_plan`, `get_pending_trip_decisions`), `search_trip_options`, four action tools (`preview_trip_change`, `commit_trip_change`, `vote_on_trip_change`, `decide_trip_change`), and `report_group_announcement`. `poll_proactive_events` has a contract and scope reserved for Plan 3 but is not registered.

Operational calls require active status and the exact bound group. Participant-aware commands resolve confirmed mapping rows and current traveler roles; connector-supplied organizer claims and display names confer no authority. The two policy fields, `travelerCanAddSuggestion` and `travelerCanProposeChange`, default to true but never grant booking or payment authority.

| Actor/operation | Required scope | Behavior |
|---|---|---|
| Paired connector setup | `connector.setup` | Register/check readiness; activate only through the readiness transaction. Ordinary tools refuse paired state. |
| Unmatched or confirmed participant reads | `trip.read` | Group-safe trip, Today, and pending decisions. |
| Unmatched or confirmed participant researches | `trip.research` | Structured stored-itinerary/Places/Routes research. |
| Confirmed human previews | `trip.propose`, plus the applicable commit scope | Read-only impact/authority snapshot. Unmatched and automated actors cannot enter the action flow. |
| Human traveler commits move/remove/replace | `trip.propose` | If preauthorized, create a proposal with one automatic proposer yes vote and run ordinary settlement. |
| Human organizer commits move/remove/replace | `trip.modify` | Create an auditable proposal and force organizer approval through protected settlement; staleness still wins. |
| Human commits suggestion | `trip.propose` | Create a suggestion proposal and ordinary settlement. Traveler preauthorization must permit it; organizer status does not force-approve this path. |
| Confirmed human votes | `trip.vote` | Upsert one vote and run the existing settlement arithmetic. |
| Confirmed human organizer decides | `trip.vote` | Approve/reject an existing proposal through protected settlement. A bot-organizer row is refused. |
| Human requests reservation preparation | Organizer: `trip.modify`; traveler: `trip.propose` | Open private organizer confirmation; confirmation additionally requires current `trip.modify`. No attempt is created by commit. |
| Active connector reports announcement | `announcement.write` | Receipt for a succeeded action owned by this connection/trip; it does not send a message. |

When traveler preauthorization is disabled, the preview reports organizer confirmation required and commit refuses with `organizer_confirmation_required`. Only reservation preparation has a private challenge implementation in this release; disabled itinerary/suggestion preauthorization does not create an automatic approval queue. Payments, cancellations, external bookings, private document access, permission changes, and connector replacement are outside MCP action authority.

## Group-safe projection

`lib/trip-agent-read-model.ts` uses explicit select lists and result mappers instead of serializing the board response. It returns trip title/destination/dates, budget/vibe/location, public schedule and activity status, venue names/ratings/hours/maps, aggregate votes, pending decision descriptions, reservation status/time, and the latest public booking workflow status. Today adds phase/date/day index, ordered items, next stop, leave-by estimate, and opening-hours risk using the existing Today helpers.

No roster or participant identities, preferences, traveler tokens, booking contact/name, confirmation number, proof artifact, private booking URL/attempt route, alternative times, or private organizer/proposal note is exposed. An unmatched viewer receives no `myVote` or capability object. A confirmed viewer receives only their own vote and capability booleans, never other voters' identities. Public trip and suggestion text remains group-visible; it is not a safe place to enter private information.

Action results and replays also use explicit allowlists; stored normalized requests, digests, safety fingerprints, and arbitrary result JSON cannot escape through a spread. Private organizer name and canonical booking-route sources are transient fingerprint inputs, not action payloads or group results. The existing authenticated V1 board projection is deliberately unchanged; this foundation does not retroactively change that older privacy contract. Provider-side chat history and logging remain outside Trip Planner's storage boundary and require organizer review during onboarding.

## Idempotency, transactions, and recovery

Registration, activation, announcement, preview, vote, and decision inputs require a UUID `requestId`. Before action persistence, the envelope's request/group/participant fields are removed: the lower-case request ID becomes the durable key, external identities become connection-and-generation-scoped HMACs, and only strict operation-specific structured fields remain. Registration participant digests are de-duplicated and sorted so provider ordering does not change command identity. Reuse is accepted only for the same connection lifecycle/trip, operation, actor, mapped traveler when applicable, and normalized request; otherwise it returns `idempotency_conflict`. A replacement generation may reuse a prior generation's request key, but it can never replay or mutate that historical action.

Registration, activation, and announcement each commit through a connection-first database transaction that owns both the command row and its domain writes. Group binding and mapping suggestions therefore roll back together; activation success can be replayed after the status transition; and an announcement receipt cannot diverge from its target action. Stored command JSON is never returned directly: the RPC and TypeScript boundary synthesize and validate the exact bounded public result. Fresh registration and activation commands are paired-only, while an exact successful command may replay after activation as long as current lifecycle and human authority still hold.

Commit accepts exactly `{ actionId, externalGroupId, externalParticipantId }`. The preview action ID is the commit key; repeating change content or a request ID is rejected by the strict schema. Current actor binding and authority are rechecked even on a retry. A resumable `received` preview computes no canonical mutation and finalizes by compare-and-set; competing workers reread the winner. The database starts the ten-minute preview clock at finalization, and expiry is inclusive at the deadline.

The execution claim locks connection → mapping → trip → human traveler before the action and any needed canonical state. It validates active status, bound group, scope, saved policy, mapping/role, fingerprint, and expiry after lock waits. Traveler locks use `FOR NO KEY UPDATE` to remain compatible with legacy foreign-key checks. Protected proposal creation compares the expected preview state under canonical locks; it never silently rebases onto a newer item, reservation, slot, or venue. Suggestions fingerprint trip existence and normalized matching open suggestions so unrelated itinerary changes do not invalidate them.

Traveler removal also uses a service-role transaction: lock the connection, then the trip, then the actor/target travelers before deleting. Direct deletion would lock a traveler first and cascade into mappings already held by a gateway command, creating a deadlock. The RPC rechecks the human organizer and same-trip target. If a previously absent connection appears while the trip lock is acquired, it aborts with internal `TP009`; the route retries in a fresh transaction up to three times, avoiding reverse lock acquisition.

The main action paths are:

| Path | Durable states and outcome |
|---|---|
| Preview | `received → previewed`; validation can finalize `refused` or `failed`. |
| Itinerary/suggestion commit | `previewed → executing → awaiting_vote / succeeded / rejected / cancelled`; expired previews cannot claim execution. |
| Reservation preparation | `previewed → executing → awaiting_confirmation`; claim replaces preview expiry with a fifteen-minute database-clock deadline. |
| Private confirmation | `awaiting_confirmation → succeeded / rejected / expired`; success means an internal draft exists, not a booked reservation. |
| Vote/decision command | Independent action `received → executing`, then the exact persisted settlement outcome. |
| Uncertain canonical commit | Stays `executing` or becomes `unknown`; never automatically run again. |

Existing proposal creation and its initial action result cannot share one transaction. The gateway therefore guarantees at-most-once execution by refusing to reset an uncertain claimed action. A crash after the domain write but before result persistence can require human reconciliation even when the plan changed successfully. Do not resubmit under a fresh request ID to bypass this state. `unknown` does not mean success and must not be announced as success.

Vote/decision preparation locks the connection, referenced preview, mapping, command action, trip, ordered travelers, proposal, and ordered votes; the shared trip lock is `FOR UPDATE`, and final apply/close revalidates current connector and human authority before committing the exact bounded tally/status/reason snapshot. Because the final SQL guard resolves the proposal’s trip from the proposal row rather than trusting the caller, both gateway and legacy paths share the same trip-first lock order and reject a stale tally with internal drift code `TP008`. A drift retries the full fresh tally/plan computation up to three total attempts, then returns the bounded database-unavailable outcome without applying or closing. A successful settlement persists its exact snapshot and replay returns that snapshot. `proposal_already_decided` distinguishes a losing concurrent settlement. A crash between preparation and final settlement can leave `executing`; exact retries resume without casting another vote and return `action_in_progress` while settlement remains ambiguous.

Reservation preparation has no provider side effect, so interrupted finalization safely resumes its internal transition or rereads durable state. It is not labeled unknown merely because a database response was lost. Announcement receipt updates lock the current connection, command, and target action; require target status succeeded; and persist only the optional message digest. Exact delivered/failed command replays return the bounded prior delivery status; a different request ID may acknowledge only the same delivery truth, while conflicting outcomes return `announcement_conflict`. No delivery worker exists yet.

## Reservation confirmation and failure boundaries

Only a `reservation_prepare` action is privately confirmable. The transaction locks connection → action → trip → current human organizer → item/candidate, checks current scope and fingerprint, and rechecks inclusive expiry after waiting. Expiry outranks rejection. Confirmation derives the organizer's trimmed name and a validated HTTPS route from canonical state: a valid booking URL is preferred, otherwise the venue's Maps URL is a venue-information handoff. It creates one `awaiting_approval` attempt with null contacts, no alternative times, one route at index zero, and the action result in the same transaction. The organizer supplies contact details on the external site. No provider, booking, payment, or cancellation call occurs.

If another active attempt already owns the item, `reservation_attempt_active` preserves the still-pending challenge until expiry; it does not adopt that attempt. Lost internal database responses are recovered by rereading the committed result, without a second insert. Reusing a consumed challenge returns `confirmation_used`. The private response exposes only action ID/status, optional attempt ID/state, and optional public item ID/venue name.

Stable refusals include `missing_scope`, `confirmed_mapping_required`, `group_mismatch`, `preview_expired`, `plan_changed`, `reservation_locked`, `destination_occupied`, `proposal_stale`, `duplicate_suggestion`, and `confirmation_expired`. Database failure becomes `database_unavailable`, never missing data or successful mutation. Terminal rejected/cancelled/refused/expired/failed states are not permission to rerun an old action.

## Research and remaining limitations

- Place/restaurant research checks the stored itinerary first, then Google Places with the corresponding category; parking uses a bounded parking query. Results carry source, rating/review count, regular hours, coordinates, Maps URL, and `verifyLiveAvailability: true`. No LLM invents venue results, and incomplete provider records are discarded. Regular hours are not a reservation-availability check. Places and Routes both abort after 10,000 ms and clear their deadline timer on success, HTTP/parse failure, and abort. Places retains its throwing internal contract; research turns provider rejection/timeout into successful bounded `upstream_unavailable` without provider text. An itinerary route endpoint lacking usable coordinates returns `coordinates_unavailable` without calling Routes.
- Driving research calls Google Routes with `TRAFFIC_AWARE`, compares traffic duration against static duration, and returns a Maps navigation URL when available. `GOOGLE_ROUTES_API_KEY` is dedicated and server-only, with separately enabled billing/quotas. It is currently unavailable; the tool reports `unavailable`. It never substitutes `GOOGLE_MAPS_API_KEY` or claims transit incident coverage.
- The trip schema has no persisted destination time zone. The internal Today reader accepts an explicit validated IANA zone and otherwise uses UTC. The MCP Today input does not expose a time zone and its adapter currently uses that UTC default; destination-local correctness is not solved. Leave-by estimates are not automatically replaced with live Routes results.
- Reservation notes are unsupported. `reservation_prepare` accepts only `kind`, `itemId`, `partySize`, and `requestedAt`, plus the participant request envelope. The strict public schema rejects `note` before an action is persisted. Future private-note support must define its storage and handoff semantics end to end.
- There is no end-user onboarding UI, live WhatsApp connection, proactive polling tool/engine, event feed, mobile companion, or automatic reconciliation worker. The connector must not claim a booking or message was sent by this gateway.
- PGlite validates migrations, transaction rollback, repeated calls, and installed lock contracts in one backend. A separate PostgreSQL 16 CI lane uses multiple clients and observed blocking-process barriers to verify vote/roster drift, simultaneous settlement, public limiter quotas, and mapped-traveler removal. Both this lane and the production smoke test passed for the shipped release.

## Deployment and rollback

Prepare both gateway migrations after existing schema and verify required server-only `TRIP_AGENT_IDENTITY_PEPPER` and `TRIP_AGENT_ALLOWED_HOSTS` before merging: `master` auto-deploys, and migrations are not automated. The production migration ledger uses different timestamps for several older migrations than this repository; do not run a blanket database push or replay that history. Apply only the two exact reviewed new SQL files through the migration API, in order, after checking the installed prerequisites. The public limiter replacement is included in the first migration; the second installs guarded traveler removal.

Production preflight explicitly sets `NEXT_PUBLIC_SITE_URL=https://your-trip-planner.example` so pairing returns the stable allowlisted MCP origin. Other environments may use `VERCEL_PROJECT_PRODUCTION_URL` as the HTTPS fallback; missing both prevents pairing. Verify configuration presence without printing secrets. Production hosts must be explicitly allowlisted; local testing may allow localhost only in isolated local configuration. Do not copy production service-role or paid API credentials into preview deployments.

Run leak/implementation scans and `npm test`, `npm run lint`, and `npm run build`; review warnings. Publish a PR covering purpose, user/developer impact, migration, configuration/deployment, rollback, validation, privacy/security, and screenshots: not applicable; no material UI change. Review its diff and CI before merge, then fetch and fast-forward local master to the merged GitHub commit.

After deployment, use a dedicated disposable test trip to verify pairing, modern client tool listing, group-safe reads, unmatched-write refusal, one organizer-approved reversible change under an exact retry, and immediate revocation. Keep credentials and provider identifiers only in process memory and clean up only that guarded test trip. The 2026-09-22 release passed these checks; results and actual production migration versions are recorded in the [release evidence](trip-agent-gateway-release.md).

For an incident, pause or revoke the affected connector and stop connector traffic first. Revert the code through a reviewed GitHub PR and verify the resulting deployment. Leave unused additive gateway schema in place during a code rollback; do not drop audit/action records or reset uncertain actions to retry them. Reconcile any already-applied canonical changes before deciding further recovery. An identity-pepper change requires a deliberate identity/re-pairing migration, not a routine rollback or bearer rotation.
